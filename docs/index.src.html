Technical manual

yolo-kalman: GPU multi-object tracker

The tracker finds objects in video and gives each object a track id. The id stays the same when the object goes fully behind an obstacle and comes back. All steps run on the GPU.

Code state of 2026-11-27, after the audit fixes. Test host: 2 × NVIDIA RTX PRO 6000 Blackwell (96 GB), CUDA 13.2 driver.

1Purpose and scope

This manual describes the yolo-kalman tracker. It tells you how the tracker works, how to install it, how to run it, and how to read the results.

The tracker has two parts:

  • Detector. Ultralytics YOLO26m finds objects in each frame. It runs as a TensorRT FP16 engine. The detector does not track.
  • Tracker. The project's own PyTorch code connects detections from frame to frame. It does not use model.track() or boxmot.

The tracker uses five methods together:

  • A Kalman filter predicts where each object moves.
  • BYTE matching uses high-score detections first and low-score detections second.
  • OC-SORT methods (OCM, OCR, ORU) correct the motion after a gap.
  • Appearance re-identification (re-ID) compares how objects look. It finds an object again after a long occlusion.
  • A batched GPU Hungarian solver finds the best matches between tracks and detections for all streams in one GPU call.

The tracker processes many video streams at the same time. Each stream has its own track ids.

NoteIds are unique in one stream only. Two streams can both have a track with id 7.

2Terms

This manual uses each term below with one meaning only.

stream
One video source. The pipeline processes S streams in parallel.
frame
One image of a stream.
chunk
8 consecutive frames of every stream. The detector processes one chunk in one batch.
detection
One box with a score, a class and an embedding, from one frame. Each stream has up to N = 160 detections per frame.
track
One object over time. A track has an id, a Kalman state and an embedding.
slot
One fixed place for a track in GPU memory. Each stream has M = 160 slots.
high / low detection
High: score ≥ 0.5. Low: 0.1 ≤ score < 0.5.
gap
The number of frames since the last trusted observation of a track.
coast
A track coasts when it has no match. Its box then comes from the Kalman prediction only.
embedding
A 512-value vector that describes how a detection looks. ResNet-18 makes it.
cost
A number for one track–detection pair. A low cost means a good match.
gate
A limit. A pair above the gate cannot match.
CUDA graph
A recorded set of GPU kernels. The GPU replays it with one call and no Python work.
host sync
A point where the CPU waits for the GPU to finish.

3GPU pipeline

The pipeline has three threads. Each thread has its own CUDA stream. Images stay in GPU memory from decode to tracking.

The engine alone processes about 3,300 images per second on one GPU at batch 32–64. NVDEC decodes about 5,000 fps for one 480p stream and about 20,000 fps for 16 decoders.

4Tracker step

One tracker step processes one frame of every stream. A step is three CUDA graphs. The step has no host sync.

4.1Matching cascade

The table gives the rows, columns, cost and limit of each stage. A pair with a cost above the limit stays unmatched.

StageTracks (rows)Detections (columns)CostGateLimit
S1TRACKED and LOSThighmin(1 − IoU, appearance distance) − 0.2 · OCM · scored² ≤ 13.277, same class group0.8

  • Appearance in S1. S1 uses the appearance distance only when it is below 0.25 and the IoU cost is below 0.5 (BoT-SORT fusion).
  • d² is the Mahalanobis distance between the Kalman prediction and the detection. 13.277 is the χ² value for 4 degrees of freedom at 0.99.
  • Class groups. Car, bus and truck are one group. Bicycle and motorcycle are one group. The detector often changes between the classes of one group.
  • Births. Each high detection with score ≥ 0.6 that no stage used starts a new TENTATIVE track. The k-th free detection goes to the k-th free slot.

5Track states

Each slot has one of four states. The state decides which stages can match the track.

A TENTATIVE track has no id. It gets the next id of its stream when it has 2 hits. This removes short false tracks from the output.

6Occlusion handling

An occlusion has three phases. The object becomes partly hidden, then fully hidden, then visible again. The tracker uses one mechanism for each phase.

6.1Partial occlusion

The box of an object becomes smaller when the object goes behind an obstacle. A small box gives a wrong size and a wrong velocity.

  • The tracker keeps a reference size for each track. The reference is a slow EMA (factor 0.9) of trusted box sizes.
  • A match is low quality when the detection score is below 0.5, or when width or height is below 0.9 × the reference size or the predicted size.
  • A low-quality match multiplies the measurement noise R by 10⁴. The size velocity is set to zero.
  • A low-quality match does not change the last observation, the OCM history or the gap counter.

6.2Full occlusion

  • An unmatched TRACKED track becomes LOST. It keeps its id.
  • The Kalman filter predicts the box in each frame. The size velocity is frozen while the track is LOST.
  • The track stays LOST for lost_buffer_s seconds (default 8 s). The limit in frames is 8 × the stream fps.

6.3Reappearance

The cascade tries to match the LOST track in this order:

  1. S1. The detection is near the prediction (IoU), or it looks the same (appearance) and is near.
  2. S3 (OCR). The detection overlaps the last real observation. This works for gaps up to 30 frames when the object stopped behind the obstacle.
  3. S4 (re-ID). The detection looks the same (appearance distance ≤ 0.25) inside a loose gate (d² ≤ 60).
  4. Id recovery. Sometimes the object comes back only partly visible and no stage matches it. It then starts a new track. When the new track is 3 to 45 frames old, the tracker compares its embedding with the LOST tracks that were already lost at its birth. A match gives the new track the old id, and the old slot becomes FREE.

6.4Observation-centric re-update (ORU)

The coasted state drifts during a long gap. ORU corrects it when the track matches again.

  1. Take the posterior saved at the last trusted observation z₀.
  2. Make up to 8 virtual observations on the straight line from z₀ to the new detection z₁.
  3. Run predict and update for each virtual observation. Longer gaps use exact multi-step predictions between them.
  4. Use the result as the new track state.

The fixed number of virtual steps keeps the GPU work constant, so ORU fits in the CUDA graph.

7Kalman filter

The filter is a batched constant-velocity model in kalman.py. It works on any leading batch shape, for example [S, M].

ItemValue
State x[cx, cy, w, h, vcx, vcy, vw, vh]
Measurement z[cx, cy, w, h]
Process noise QStandard deviation proportional to box w and h: 1/20 for position, 1/160 for velocity (BoT-SORT xywh filter).
Measurement noise R(w/20)², (h/20)², multiplied by (1 − score) (NSA Kalman filter). Low-quality matches: × 10⁴.
Initial covariance2/20 · size for position, 10/160 · size for velocity.
Multi-step predictpredict_dt: exact Fdt and Σ Fj Q FjT in closed form. dt = 1 equals predict.
GatingSquared Mahalanobis distance d² of each detection to each track.

The update uses a Cholesky solve of the 4×4 innovation covariance. When the tracker is compiled, the solve is written element by element (UNROLLED_4X4). The compiler then fuses it into a few kernels. Predict and update use element-wise products, not batched 8×8 matrix multiplies, for the same reason.

tests/test_kalman.py compares predict, update and d² with a NumPy reference.

8Assignment solver

Each cascade stage must pick the best set of track–detection pairs. The solver is an exact Hungarian method (Kuhn–Munkres) in shortest-augmenting-path form. It runs as one CUDA kernel for all streams. The torch custom op is yolo_kalman::lap_batch.

8.1Problem

The solver gives the same optimum as lap.lapjv(c, extend_cost=True, cost_limit=L). In that problem each row and each column may stay unmatched at cost L/2. The optimum is:

min  Σ over matched pairs (c_ij − L)   +   L · (R + C) / 2
  • A pair with c > L never helps, so the solver forbids it.
  • A pair with c = L ties with "unmatched". The solver matches it, as lapjv does.

8.2Kernel

  • One thread block per stream. One launch solves all streams.
  • 256 threads find the rows and columns that have at least one allowed pair. They compact them in order.
  • The threads copy the compacted costs to shared memory when they fit the device limit. Larger problems read global memory through the column index.
  • One warp runs the search. Columns are spread over the 32 lanes. A warp-shuffle reduction finds the minimum. Ties go to the lowest column index, so the result is deterministic.
  • Duals are float64. Costs are float32. There is no epsilon and no iteration limit, so the result is optimal.
  • All data-dependent loops are inside the kernel. A solve is one fixed launch with no host sync. CUDA graphs can record it.
NoteThe RTX PRO 6000 allows 99 KB of shared memory per block. This holds about 22,600 staged cells (150 × 150). The 160 × 160 maximum uses the global-memory path. test_crowd_size_dense derives a size that forces the global path on any GPU.

The kernel is built on first use with torch.utils.cpp_extension (about 40 s, nvcc from /usr/local/cuda). The build is cached in ~/.cache/torch_extensions.

8.3Solver speed

Sparse tracking-like costs: one true pair, three possible wrong pairs per row, all other pairs gated. Times include launch overhead, outside CUDA graphs. Inside the tracker graph one solve takes about 7.5 µs.

8.4Proof of exactness

  • Unit tests (tests/test_assign.py): the total cost equals scipy linear_sum_assignment and lapjv. Cases: random rectangular problems, 1×N, N×1, empty, all gated, costs at the limit, 3e38 and 6.55e4 values, NaN and inf, many ties, 32 mixed-size streams, problems up to the global-memory path, CUDA-graph replay and torch.compile.
  • Tracker: the GPU cascade gives frame-identical output to the lapjv cascade on the synthetic scenes (test_gpu_hungarian_cascade_matches_lapjv).
  • Real data: 8,536 of 8,536 recorded problems from 12 real clips give the same total cost as lapjv. 222 of them (2.6 %) have a different optimal assignment with the same cost.

8.5Use the solver

Call lap_batch(cost, row_mask, col_mask, limit). All tensors must be on the GPU.

ArgumentShape and typeMeaning
cost[S, R, C] float32Cost of each row–column pair, for each stream. A low cost is a good match.
row_mask[S, R] boolThe rows (tracks) that take part.
col_mask[S, C] boolThe columns (detections) that take part.
limitfloatThe cost limit for all streams. A pair above the limit cannot match.
return value[S, R] int64The matched column of each row. -1 means unmatched: the row is masked, or all its allowed pairs are above the limit.

The result has the same optimum as one lap.lapjv(cost[s][rows][:, cols], extend_cost=True, cost_limit=limit) call per stream.

import torch
from yolo_kalman.assign import lap_batch

# 2 streams, 3 tracks (rows) x 4 detections (columns); cost = 1 - IoU
cost = torch.tensor([[[0.10, 0.90, 0.95, 0.70],
                      [0.85, 0.20, 0.90, 0.95],
                      [0.90, 0.90, 0.90, 0.90]],
                     [[0.30, 0.25, 9e4, 9e4],
                      [0.20, 0.40, 9e4, 9e4],
                      [9e4, 9e4, 9e4, 9e4]]], device="cuda")
rows = torch.tensor([[True, True, True], [True, True, False]], device="cuda")
cols = torch.ones(2, 4, dtype=torch.bool, device="cuda")
print(lap_batch(cost, rows, cols, 0.8).tolist())   # [[0, 1, -1], [1, 0, -1]]
  • Stream 0: row 2 stays unmatched. All its costs are above 0.8.
  • Stream 1: row 0 gets column 1 and row 1 gets column 0. The total is 0.25 + 0.20 = 0.45. The other choice costs 0.30 + 0.40 = 0.70.
  • Stream 1: row 2 is masked, so its result is -1.

8.6How the tracker uses the solver

The tracker calls the solver 6 times in each step, in MultiStreamTracker._gmatch_core. Each call solves all streams.

  1. Make the cost plane of the stage for all streams.
  2. Set each gated pair to BIG (6 × 10⁴). This value is above every limit, so the pair cannot match. A pair is gated when it fails the Mahalanobis gate, is in a different class group, or has no embedding.
  3. Set row_mask to the tracks of the stage that are not matched yet.
  4. Set col_mask to the detections of the stage that are not used yet.
  5. Call lap_batch with the stage limit (S1 0.8, S2 0.5, S3 0.7, S4 0.25, S5 0.7).
  6. Mark the matched rows and the used columns. The next stage starts from these masks.

Call 6 is id recovery. Its rows are LOST tracks. Its columns are young TRACKED tracks. Its cost is the embedding distance. Its limit is 0.25.

All 6 calls are inside the match CUDA graph, so the CPU does no work for them during replay.

To use the CPU reference cascade with lap.lapjv, set TrackerConfig(assign="lapjv"). The scripts track.py, bench.py and eval_synth.py accept --assign lapjv.

9Procedures

CautionRun all project Python through ./run.sh. It removes LD_LIBRARY_PATH. The host path loads cuDNN 9.20 before the venv cuDNN 9.24, and every convolution then fails.

9.1Install the environment

  1. Go to the project folder.
    cd ~/GWorkspace/yolo-kalman
  2. Sync the environment. This installs torch 2.14 (cu130), TensorRT 11.5, PyNvVideoCodec, motmetrics and the dev group (pytest).
    ~/.local/bin/uv sync
  3. Make sure that nvcc is at /usr/local/cuda/bin/nvcc. The solver kernel needs it for the first build.

9.2Get the clips

  1. Download the Wikimedia Commons 480p transcodes to clips/.
    ./run.sh scripts/download_clips.py
  2. Read meta/clips_index.tsv for the licence and source page of each clip.
CautionDownloaded clips are untrusted data. run.sh starts Python with -I, so files in the clip folder cannot replace Python modules.

9.3Export the detector engine

  1. Export the TensorRT FP16 engine with the NMS-free head. Run the command in the project folder. The script downloads yolo26m.pt and writes the engine to models/.
    ./run.sh scripts/export_trt.py yolo26m.pt --nms-free

9.4Make the synthetic clips

  1. Make the occlusion clips and their ground truth in data/synth/.
    ./run.sh scripts/make_synthetic.py

9.5Run the tests

  1. Run all tests in strict mode.
    REQUIRE_E2E=1 ./run.sh -m pytest -rs -q
  2. Make sure that the result is 23 passed with no skip.
NoteThe two end-to-end tests need the engine, a real clip and a synthetic clip. These files are not in git. Without REQUIRE_E2E=1 the tests skip and pytest still reports success. A skip means that the occlusion result is not verified.

To run one test, use -k:

./run.sh -m pytest -q -k test_crowd_size_dense

9.6Evaluate on the synthetic clips

  1. Run the evaluation and the ablations. Add --overlay to write videos.
    ./run.sh scripts/eval_synth.py --overlay
  2. Read results/synth/metrics.md.

9.7Track real clips

  1. Track all clips as parallel streams on one GPU and write overlay videos.
    ./run.sh scripts/track.py clips/*.webm --out results/real --overlay
  2. Open results/real/*_tracks.mp4 to see ids and trails.
  3. Read results/real/summary.json for id counts, fragmentations and timings.

Useful options: --no-reid, --lost-s 8.0, --assign lapjv, --classes 0 2 5, --max-frames N, --gpu 1.

9.8Measure throughput

  1. Run the benchmark on both GPUs. Each setting runs 3 times. The median run is reported.
    ./run.sh scripts/bench.py --streams 1 4 8 16 32 --gpus 0 1 --frames 1200 --repeats 3 --assign gpu_hungarian --tag mytag
  2. Make a markdown table from the result.
    ./run.sh scripts/bench_table.py "mytag"

The clips limit a stream to about 1,350 frames. To get less noise, use more repeats, not more frames.

9.9Use the tracker from Python

from yolo_kalman.pipeline import Pipeline, PipelineConfig
from yolo_kalman.tracker import TrackerConfig

cfg = PipelineConfig(classes=[0, 2], tracker=TrackerConfig(lost_buffer_s=8.0))
pipe = Pipeline(["clips/a.webm", "clips/b.webm"], gpu=0, cfg=cfg)
for r in pipe.run():                      # one StreamResult per stream
    for ids, boxes, scores, cls in r.tracks:   # one entry per frame
        ...

Create the Pipeline before you open other NVDEC decoders. The tracker records its CUDA graphs in the constructor. Decoder threads on the legacy stream can break a recording.

13Limitations

  • No permissively licensed detector is built. The Detector protocol accepts one (YOLOX, RT-DETR, D-FINE).
  • Real-clip quality is not verified, because the clips have no ground truth.
  • ResNet-18 ImageNet features are not a trained re-ID model. Objects that look the same, for example cars of the same colour, can get the wrong id. The Mahalanobis gate and the class groups reduce this risk.
  • HOTA is a re-implementation, not TrackEval.
  • Ids are unique per stream only.
  • When several optimal assignments exist, the GPU solver can choose a different one than lapjv. The total cost is the same.
  • The GPU cascade always runs the ORU branch, masked per slot.
  • The pipeline is not bit-deterministic from run to run.
